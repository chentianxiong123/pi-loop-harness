# 分形解耦架构：面向 AI 并行开发的完整体系

## 序言
这套体系的目标只有一个：让多个 AI Agent 并行开发时，互相不踩脚，代码可检索，意图不跑偏，测试可验证。

它不追求优雅，不追求抽象，不追求人看得舒服。它追求的是显式。一切都可以被 grep 找到，一切都可以被路径定位，一切都可以被测试验证。

## 第一章：架构总览
整个系统由三大层组成，每一层的职责边界极其清晰，不允许越界。

```
第一层：业务函数目录（系统的心脏）
     ↓
第二层：基础设施目录（系统的工具箱）
     ↓
第三层：胶水层（系统的组装车间）
```

这三层之外，还有两个横跨所有层级的角色：

- **SPEC 文档**：对齐 Agent 生成，AI 读的开发指引
- **契约文件**：主 Agent 翻译，代码层面的接口定义

## 第二章：第一层——业务函数目录

### 职责
存放所有业务逻辑。这是系统的心脏。每一个文件代表一个具体的业务动作，文件名就是函数名。

### 目录结构
```
业务/
├── 磁盘监控/
│   ├── 采集/
│   │   ├── smart信息.go
│   │   ├── 温度.go
│   │   └── 健康状态.go
│   ├── 展示/
│   │   ├── 仪表盘.go
│   │   └── 磁盘卡片.go
│   └── 告警/
│       └── 温度阈值.go
├── 用户/
│   ├── 认证/
│   │   └── 登录.go
│   └── 权限/
│       └── 角色检查.go
```

### 规则
- 目录名就是业务域。不用 handler、controller、service 这种技术性词汇。
- 文件名就是业务动作。一个文件一个函数，文件名等于函数名。
- 纯粹业务逻辑。这里不允许出现任何技术性噪音，不 import 外部库，不处理 HTTP，不碰数据库连接。

### 为什么这样
因为 AI Agent 找代码的方式是 grep 和 ls。目录结构本身就是导航，文件名本身就是文档。当 Agent 要找"温度阈值告警"的代码时：

```
ls 业务/磁盘监控/告警/
grep -r "温度阈值" 业务/
```

一步到位，零 token 浪费。

## 第三章：第二层——基础设施目录

### 职责
存放所有通用技术性函数。这是系统的工具箱，也是轮子仓库。所有可复用的公共方法都在这里注册。

### 目录结构
```
基础设施/
├── 转换/
│   ├── json序列化.go
│   ├── json反序列化.go
│   ├── 时间格式化.go
│   └── 字节转字符串.go
├── 数据/
│   ├── sqlite连接.go
│   ├── sqlite查询.go
│   ├── sqlite写入.go
│   └── 事务执行.go
├── 网络/
│   ├── http请求.go
│   ├── http响应.go
│   └── 参数解析.go
└── 系统/
    ├── 命令执行.go
    ├── 文件读取.go
    └── 环境变量.go
```

### 规则
- 这里没有任何业务逻辑。只放通用的、可被所有业务调用的技术性函数。
- 造新轮子之前，必须先 grep 这里。
- 造好的新轮子，必须在这里注册。注册方式就是新建一个文件，文件名就是函数名。

### 为什么这样
这是"全局同构图"的现实版。不需要哈希，不需要语义检索，只需要目录和文件名。AI Agent 想找"执行外部命令"的轮子：

```
ls 基础设施/系统/
# 看到 命令执行.go，打开，直接复用
```

## 第四章：第三层——胶水层

### 职责
管理部署，把业务函数和基础设施函数组装成可以跑起来的项目。这一层没有任何业务逻辑，也没有任何通用工具逻辑。

### 目录结构
```
胶水/
├── 接口/                    ← 契约文件的存放地
│   ├── 业务/
│   │   ├── 磁盘监控/
│   │   │   ├── 采集.go      # 定义函数签名，不写实现
│   │   │   ├── 展示.go
│   │   │   └── 告警.go
│   │   └── 用户/
│   │       ├── 认证.go
│   │       └── 权限.go
│   └── 基础设施/
│       ├── 数据.go
│       ├── 转换.go
│       └── 系统.go
├── 组装/
│   ├── 主程序.go            # 把业务和基础设施拼成一个进程
│   ├── 定时任务.go          # 把采集函数注册成 cron
│   └── http接口.go          # 把展示函数暴露成 HTTP 端点
├── 进程/
│   ├── 启动.sh
│   ├── 停止.sh
│   └── 健康检查.sh
└── 部署/
    ├── docker-compose.yml
    └── Dockerfile
```

### 规则
- 契约文件只声明"形状"，不写"实现"。
- 业务函数完全不需要知道自己会被怎么用。它可能被主程序调用，也可能被定时任务调度，也可能被 HTTP 接口暴露。
- 修改契约等于重新开火。所有正在跑的工作间全部销毁，带着新契约重新启动。

### 契约文件示例

```
胶水/接口/业务/磁盘监控/采集.go：

package 接口

// 采集域的函数契约
// 所有实现必须严格匹配这些签名

type 温度采集器 interface {
    获取温度(磁盘串号 string) (温度 int, 错误 error)
}

type SMART信息采集器 interface {
    获取SMART信息(磁盘串号 string) (信息 SMART信息, 错误 error)
}

// SMART信息 是采集域的数据结构契约
type SMART信息 struct {
    温度 int
    通电时间 int
    重定位扇区数 int
    状态 string
}
```

## 第五章：SPEC 文档

### 职责
SPEC 是 AI 写给 AI 看的开发指引。它在对齐阶段由审讯 Agent 自动生成，冻结后成为所有后续工作间的唯一指引。

### 生成流程
```
人：给一个模糊意图
    ↓
对齐 Agent：开始刨根问底
    ↓
人：回答、澄清、纠正
    ↓
对齐 Agent：根据对话，自动生成 SPEC 文档
    ↓
SPEC 冻结
```

### 示例
```
# SPEC: 硬盘 SMART 信息检测仪表盘

## 功能1：磁盘采集
- 每30秒采集一次本机磁盘 SMART 数据
- 采集方式：调用 smartctl 命令，解析 JSON 输出
- 采集字段：序列号、型号、温度、通电时间、重定位扇区数

## 功能2：数据持久化
- 存储介质：SQLite 单文件
- 每次采集生成一个不可变快照，不做 upsert
- 磁盘身份由序列号唯一确定

## 功能3：Web 展示
- 展示方式：htmx + Go 服务端渲染
- 磁盘卡片每30秒自动刷新
- 温度超过60度时，卡片状态显示为 alert

## 功能4：告警
- 温度阈值：60°C
- 超过阈值时，状态字段返回 alert
- 不需要邮件通知，仅页面高亮
```

## 第六章：开发流水线

### 完整流程
```
业务对齐阶段
    ↓
探索阶段
    ↓
主 Agent 翻译 SPEC → 契约
    ↓
并行实现阶段
    ↓
并行测试阶段
    ↓
审查合并
    ↓
联调回归
```

### 各阶段详解

#### 1. 业务对齐阶段
唯一禁止产出的阶段。对齐 Agent 只做一件事：提问、追问、反问、确认。它的唯一产出，是一份经人确认的、无歧义的 SPEC 文档。

| 允许 | 禁止 |
|------|------|
| 提问 | 写代码 |
| 反问 | 写 Demo |
| 复述确认 | 触发搜索 |
| 列出矛盾 | 打开工作间 |

#### 2. 探索阶段
最自由的并行阶段。可以同时触发多个探索工作间，每个探索不同的技术路线，产出的是知识（探索报告），不是代码。

```
主 Agent：探索用 smartctl 还是直接读 /sys/block
    ↓
工作间 A：smartctl 方案 Demo
工作间 B：/sys/block 方案 Demo
    ↓
返回探索报告
```

这个阶段不需要遵守目录宪法，可以用 Python 快速生成 Demo。唯一要求：每个探索分支必须在固定时间内返回报告。

#### 3. 契约生成阶段
主 Agent 基于 SPEC + 探索报告，在 胶水/接口/ 下生成契约文件。契约冻结后，所有工作间只读不可改。

#### 4. 并行实现阶段
多工作间 + 多 Agent 并行开发。

```
主 Agent 派发任务
    ↓
┌────────────┬────────────┬────────────┐
│ 工作间 A    │ 工作间 B    │ 工作间 C    │
│ (Docker)   │ (Docker)   │ (Docker)   │
│ (worktree) │ (worktree) │ (worktree) │
│ 查→改→审   │ 查→改→审   │ 查→改→审   │
└────────────┴────────────┴────────────┘
    ↓
测试收尾，通过则合并入主干
```

#### 5. 测试阶段
函数级测试，一个函数一个测试文件，放在同一作用域：

```
业务/磁盘监控/采集/
├── smart信息.go
├── smart信息_test.go
├── 温度.go
└── 温度_test.go
```

测试也可以并行，因为函数间没有共享状态。

#### 6. 联调回归
人拿原始 SPEC 做最终回归。这是唯一需要人介入全局视角的环节。

## 第七章：多 Agent 与子 Agent

### 多 Agent：查、改、审分离
```
查找 Agent → 修改 Agent → 审查 Agent
```

- **查 Agent**：只负责 grep、ls、读文件。不写代码。
- **改 Agent**：只负责写。不看整个代码库，只看查 Agent 给它的上下文。
- **审 Agent**：只负责对。拿查 Agent 的输入和改 Agent 的输出逐行比对。

### 子 Agent：作用域就是它的宇宙
主 Agent 派发任务时，会指定子 Agent 的作用域。子 Agent 只在这个作用域里跳舞，权限被 harness 强制限制。它不知道自己不在的目录里有什么。

### 隔离机制
三层隔离，层层递进：

- **Git worktree**：文件系统级别的物理隔离。每个工作间独立分支，互不触碰。
- **Docker 容器**：环境级别的物理隔离。独立依赖，独立编译，独立测试。
- **独立测试收尾**：验证级别的物理隔离。通过才能合入，不通过则销毁重建。

## 第八章：防止跑偏的回归原则

### 核心铁律
每个工作间，每次迭代，都必须先把原始需求重新读一遍。

这不是软提醒，是写进 system prompt 的硬规则：

```
子 Agent 修改前：
打开 SPEC 文档，逐条对照本任务是否属于其中的一部分。
不属于，立即停止，报告主 Agent。

审查 Agent 审核时：
拿原始 SPEC 逐条比对 diff。
每一条修改必须能追溯到 SPEC 中的某一条。
找不到来源的修改，直接拒绝合入。
```

### 回归节点
| 节点 | 回归动作 |
|------|----------|
| 业务对齐结束 | 产出 SPEC，冻结为不可变文档 |
| 探索工作间启动 | 必须引用 SPEC 中的具体条目 |
| 实现子 Agent 开工前 | 读 SPEC，确认自己在边界内 |
| 实现子 Agent 每次修改后 | 对照 SPEC 自查 |
| 审查 Agent 审核时 | 逐条 diff 追溯到 SPEC |
| 主 Agent 合并时 | 全局回归，确认未跑偏 |
| 联调阶段 | 拿起原始 SPEC，再次整体比对 |

## 第九章：上下文预算管理

代码细分到函数粒度，最深层的原因是为了控制每个 Agent 的上下文窗口永远塞不满。

一个子 Agent 在 业务/磁盘监控/采集/ 里干活，它只需要读这个目录下的三五个文件，加上 SPEC 里的相关条目。整个上下文可能就几千 token。它不会乱，不会忘，不会因为读了一万行无关代码而开始瞎编。

上下文窗口就是 AI 的内存。内存越满，错误越多。这套架构让每个 Agent 的"内存"永远只装它该装的。

## 第十章：模板代码

针对不同项目类型，准备三套模板。模板本身不是给人复制粘贴的，是给主 Agent 在派发任务前，先判断项目类型，然后从对应模板里 fork 出工作间。

### 模板一：网页仪表盘型
```
go + sqlite + htmx
适合：监控面板、报表系统、后台管理。
```

### 模板二：CLI 工具型
```
go + sqlite（可选）+ 命令行参数
适合：开发工具、自动化任务、运维命令。
```

### 模板三：API 服务型
```
go + sqlite + 纯 JSON
适合：给其他系统提供数据接口。没有 htmx 和 HTML，全部 JSON 进出。
```

### 模板的本质
模板是一种"预置的契约"。它定义了目录结构、构建方式、测试方式、启动方式。子 Agent 被激活时，不需要问"这个项目长什么样"，因为模板已经回答了。

## 终章：这套架构的上限与边界

### 它能做到的
一切可以被拆成独立函数，且函数的正确性不依赖其他函数的系统。具体来说：

- 企业内部系统
- 监控/运维/诊断工具
- 开发工具
- 数据管道/自动化
- CLI 工具

这类系统占所有商业软件的 90%。

### 它做不到的
正确性存在于函数与函数之间的隐含关系里的系统。这类系统的特征是：每个函数局部正确，但系统整体可能是错的。数据库内核、操作系统、编译器、真正的分布式系统，都属于这一类。

### 真正的上限
这套架构的上限，取决于人能在探索阶段看到多远。实现阶段的效率已被推到极致，不构成瓶颈。真正的瓶颈永远在前面：对齐阶段能不能问出对的问题，探索阶段能不能找到对的路。

这两件事，本质上还是人的直觉和品味在起作用。但这个体系已经为它们留出了最好的位置。
