# 架构总纲：平台（TS）与模板（Go）

> 本文档记录 pi-loop-harness 的核心架构认知。
> 对齐日期：2026-08-27；修订日期：2026-09-12。
> 一句话：**pi-loop-harness 是一个 TypeScript agent 控制监管平台；`framework/` 是可选的 Go 应用项目模板，不是平台本身。**

---

## 1. 不是两个框架，是平台与模板

早期文档把 `.pi/`（TS）和 `framework/`（Go）说成"两个框架配合"。这是错的。

| | `.pi/` 平台核心 | `framework/` 应用模板 |
|---|---------|------------|
| **是什么** | agent 控制监管平台本体 | Go 应用项目骨架模板 |
| **语言** | TypeScript | Go |
| **运行时** | Pi agent (Node.js) | 独立二进制 |
| **回答的问题** | "agent 怎么自主、可靠地干活" | "被监管的目标工程长什么样" |
| **地位** | 核心 — 平台本身 | 可选 — 模板之一 |
| **可替换** | 不行，这是平台 | 可以换成 TS/Python/Rust 骨架 |

`framework/` 只是平台**可选的目标工程骨架**之一。你可以用它，也可以不用，用别的骨架。平台不依赖 `framework/`。

---

## 2. 平台核心：`.pi/`（TypeScript）

这是 pi-loop-harness 的本体。

### 2.1 harness —— 马具，约束工程

名字是比喻：要跑的是 AI 这匹马，**马具是套在它身上、让它按既定路线跑的约束装置**。

约束工程的三种硬约束（不是 prompt 软提醒，是结构层的强制）：

1. **工具门禁**：当前阶段能调什么工具，由代码拦截，阶段错了工具不存在。
2. **输出契约**：每步输出必须满足 verify 条件，不满足就不算完成。
3. **上下文锁**：每轮 agent 只看到它当前该看的（spec + 阶段 + 当前 task），其他历史不可见。

> 三者互补：**看不见 → 做不了 → 做不完。** 层层收窄，没得跑偏。

### 2.2 loop —— 循环工程

回答 "agent 在时间轴上的编排"：

- 什么时候开始跑
- 什么时候该继续迭代
- 什么时候该停下来
- 上次做到哪，下次从哪接
- 多个 agent 怎么协作

### 2.3 目的

**让 AI 自主干活**：

- 不再由人类手动逐轮 prompt
- 系统自带循环与停止条件
- 结果不依赖单次上下文窗口，靠外部持久化状态
- 进程自行运转，结果主动交付

> 人不再写 prompt，人写 **loop**。

### 2.4 载体：Pi 插件（TypeScript）

> constraint/loop 引擎全部实现为 Pi 插件（TypeScript），Pi 是实际干活的 agent。

Pi = `@earendil-works/pi-coding-agent`（本机 `pi 0.84.2`，数据 `~/.pi/agent`）。它自带完整扩展系统，恰好提供约束工程所需的全部事件拦截点：

| 约束工程 | Pi 插件事件 | 能力 |
|---------|------------|------|
| **工具门禁** | `pi.on("tool_call")` | 可改 `event.input`，可 `{ block, reason, terminate }` 拦截 |
| **上下文锁** | `pi.on("context")` | 每轮 LLM 调用前过滤/注入 messages |
| **输出契约** | `pi.on("tool_result")` / `message_end` / `turn_end` | 修改结果、替换消息、判 verify |
| **Spec 注入** | `before_agent_start` | 注入 message + 改 system prompt |
| **状态持久化** | `pi.appendEntry()` | 跨重启存活（外部 State）|
| **编排指令** | `pi.registerCommand()` | `/loop` `/workspace` 等自定义命令 |
| **子 agent / 事件触发** | `pi.registerTool()` + RPC | 工作间协调、多 agent 调度 |

## 3. 应用模板：`framework/`（Go）

**framework/ 是被平台监管的目标工程骨架模板。** 它不是平台的一部分，平台不依赖它。

- 提供开箱即用的工程骨架：数据库、配置、API 壳、部署形态、通用 CRUD/权限底座
- 技术选型：**GO + SQLite + HTMX + Alpine.js**（+ daisyUI + SSE）
- 单一二进制，零 npm，零构建，SSR，事件驱动

你可以用 `framework/` 作为目标工程的起点，也可以不用——换任何其他骨架。平台的 `.pi/` 流水线能监管任何项目，不限于 Go。

---

## 4. 分层边界

| 层面 | 规则 |
|------|------|
| **编排层**（主线 agent） | 纯函数，无副作用，只读 spec 和摘要状态 |
| **执行层**（子 agent） | 允许副作用（HTTP / 写文件 / 数据库），但过程不回流主线 |

> **主线纯，子 agent 可脏。脏的东西留在子 agent 内部，只有清洁的摘要回传。**
> 子 agent 可以跑两百轮，主线只需要一行摘要。

---

## 5. 方法论链条

```
Spec（单一真相源）
  → 约束工程（门禁 / 契约 / 锁，怎么强制对齐）
    → 上下文最小化（每个 agent 只给它该看的）
      → 子 agent 隔离（对齐的执行单元）
        → 事件驱动（触发机制，不轮询）
          → 验证测试（通过才算完成）
            → 探索优先（读多写少，探索 45% / 编码 20% / 验证 35%）
```

---

## 6. 协议层：瘦到不能再瘦

- **SKILL.md 不是文档，是 Agent 的启动指令**：触发规则 + 几条关键动作
- 每个文件只定义一件事，不超过 30 行
- 协议层不依赖脚本，读/写/commit 用 CLI 原生操作
- 事件驱动：Agent 不做主动决策，收到指令才动

**STATUS.md 是唯一的交流通道** —— 不接受 Agent 直接通信；文档是主权，Agent 是工具。
