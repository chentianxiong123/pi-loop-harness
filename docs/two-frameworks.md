# 双框架总纲：AI 框架 × GO 项目框架

> 本文档记录 pi-loop-harness 主线的核心架构认知。
> 对齐日期：2026-08-27
> 一句话：**用「AI 框架 + GO 项目框架」两者配合，搭建一个可以并发进行、可以自动进行、可以有银弹的软件工程项目。**

---

## 1. 两个框架，不是一回事

这里存在**两个"框架"**，它们属于不同维度，不能混为一谈。

| | AI 框架 | GO 项目框架 |
|---|---------|------------|
| 是什么 | harness（马具）+ loop（循环工程） | 类似 SpringBoot / 若依 那样的工程脚手架 |
| 性质 | AI 的方法论与约束体系 | 软件工程的应用骨架 |
| 与技术栈关系 | 与语言无关，不绑定任何工具链 | 明确技术选型：**GO + SQLite + HTMX** |
| 回答的问题 | "AI 该怎么自主、可靠、持续地干活" | "落地成什么样的工程结构" |

---

## 2. AI 框架：harness + loop

**框架一，AI 框架**，这是 pi-loop-harness 的本体。

### 2.1 harness —— 马具，约束工程

名字是比喻：要跑的是 AI 这匹马，**马具是套在它身上、让它按既定路线跑的约束装置**。

约束工程的三种硬约束（不是 prompt 软提醒，是结构层的强制）：

1. **工具门禁**：当前阶段能调什么工具，由代码拦截，阶段错了工具不存在。
2. **输出契约**：每步输出必须满足 verify 条件，不满足就不算完成。
3. **上下文锁**：每轮 agent 只看到它当前该看的（spec + 阶段 + 当前 task），其他历史不可见。

> 三者互补：**看不见 → 做不了 → 做不完。** 层层收窄，没得跑偏。

### 2.2 loop —— 循环工程

回答 "agent 在时间轴上的编排"：

- 什么时候开始跑
- 什么时候该继续迭代
- 什么时候该停下来
- 上次做到哪了，下次从哪接
- 多个 agent 怎么协作

### 2.3 AI 框架的目的

**让 AI 自主干活**：

- 不再由人类手动逐轮 prompt
- 系统自带循环与停止条件
- 结果不依赖单次上下文窗口，靠外部持久化状态
- 进程自行运转，结果主动交付

> 人不再写 prompt，人写 **loop**。

### 2.4 与语言无关

约束工程不是脚手架，不绑定任何工具链。它是方法论层。
它给的是**原则和边界**，不是**路径和模板**。

---

## 3. GO 项目框架：工程应用的骨架

**框架二，项目框架**。它是具体软件工程项目的技术底座，类比 SpringBoot / 若依。

- 提供开箱即用的工程骨架：数据库、配置、API 壳、部署形态、通用 CRUD/权限底座
- 技术选型：**GO + SQLite + HTMX**（+ templ + daisyUI + SSE）
- 单一二进制，零 npm，零构建，SSR，事件驱动

GO 项目框架是**承载 AI 框架落地的工程层**，但它本身不是 AI 框架，也不属于 pi-loop-harness 的 AI 方法论层。

---

## 4. 两者配合：目标系统

```
GO 项目框架（骨架）          AI 框架（灵魂）
SpringBoot/若依式底座   ×   harness + loop 引擎
      │                        │
      └──────────┬─────────────┘
                 ▼
   一个可以并发进行、可以自动进行、可以有银弹的
               软件工程项目
```

| 目标能力 | 靠谁 |
|---------|------|
| **并发进行** | GO 项目框架的工程底座 + goroutine/worker pool |
| **自动进行** | AI 框架的 loop 循环编排 |
| **有银弹** | 组合本身：约束工程保证不跑偏，循环工程保证持续推进，骨架保证工程完备 |

> 若依给的是模板和路径，AI 框架给的是原则和边界。二者不冲突，反而互补。
> 若依式骨架里住进 loop 式 AI 引擎 = 软件工程本身由这套系统自主完成，人只设计循环。

---

## 5. 分层边界

| 层面 | 规则 |
|------|------|
| **编排层**（主线 agent） | 纯函数，无副作用，只读 spec 和摘要状态 |
| **执行层**（子 agent） | 允许副作用（HTTP / 写文件 / 数据库），但过程不回流主线 |

> **主线纯，子 agent 可脏。脏的东西留在子 agent 内部，只有清洁的摘要回传。**
> 子 agent 可以跑两百轮，主线只需要一行摘要。

---

## 6. 方法论链条（与选型文档一致）

```
Spec（单一真相源）
  → 一切皆函数（把 spec 变成可执行的结构）
    → 约束工程（门禁 / 契约 / 锁，怎么强制对齐）
      → 上下文最小化（每个 agent 只给它该看的）
        → 子 agent 隔离（对齐的执行单元）
          → 事件驱动（触发机制，不轮询）
            → 验证测试（通过才算完成）
              → 探索优先（读多写少，探索 45% / 编码 20% / 验证 35%）
```

## 7. 待解决的具体定位问题

主线方向已定，但三个落点问题仍需确认：

1. **交付物形态**：这个软件工程项目最终是给普通人用的产品，还是驱动所有 AI 工作的元工具？
2. **GO 框架的"若依感"强度**：需要代码生成器 / 页面脚手架，还是只要稳定底座 + AI 引擎入驻？
3. **银弹的落点**：更多靠 AI 框架的自主循环（引擎），还是 GO 框架的工程完备（骨架）？
